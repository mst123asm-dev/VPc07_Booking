# Правила разработки проекта

## 1. Общие требования

Проект разрабатывается как production-level приложение.

Обязательные требования:

* не использовать временные решения, костыли и дублирование логики;
* не изменять рабочий код без необходимости;
* перед изменением анализировать цепочку вызовов и зависимости;
* сохранять существующую архитектуру;
* изменения выполнять небольшими этапами;
* после каждого существенного изменения выполнять проверку;
* не переписывать целые файлы без необходимости;
* не менять рабочую функциональность ради косметического улучшения.

---

## 2. PostgreSQL Driver — ЗАПРЕЩЕНО изменять

Файл:

`postgres_driver.py`

является готовым, протестированным и переиспользуемым инфраструктурным компонентом.

### Агенту запрещено:

* изменять `postgres_driver.py`;
* рефакторить `postgres_driver.py`;
* переименовывать классы, методы или параметры;
* изменять существующий API;
* изменять механизм пула соединений;
* изменять управление соединениями;
* изменять транзакционную логику;
* изменять обработку `commit` / `rollback`;
* изменять обработку ошибок;
* добавлять в драйвер бизнес-логику бронирования;
* добавлять в драйвер модели или сущности предметной области.

Если для системы бронирования не хватает функциональности драйвера, сначала сообщить об этом пользователю.

Самостоятельно изменять `postgres_driver.py` запрещено.

---

## 3. Использование PostgreSQL Driver

Система бронирования должна использовать существующий `PostgresDriver` через его публичный API.

Необходимо использовать существующие методы драйвера:

* `execute_query()`;
* `fetch_one()`;
* `fetch_all()`;
* `transaction()`.

Не создавать второй механизм подключения к PostgreSQL.

Не создавать дополнительные connection pool.

Не использовать прямое управление соединениями приложения в обход `PostgresDriver`.

---

## 4. Бизнес-логика

Бизнес-логика системы бронирования не должна находиться в `postgres_driver.py`.

Она должна располагаться в соответствующих слоях приложения.

Например:

* модели / сущности;
* repository;
* services;
* handlers / controllers;
* application logic.

Драйвер отвечает только за работу с PostgreSQL.

---

## 5. Архитектура

Не смешивать:

* работу с БД;
* бизнес-логику;
* HTTP/API;
* пользовательский интерфейс;
* конфигурацию;
* валидацию;
* тесты.

Каждый слой должен иметь одну понятную ответственность.

## 5.1. Предметная область проекта

Проект представляет собой рабочую систему бронирования столиков ресторана.

Цель проекта — не демонстрационный прототип, а компактное production-level приложение с реальной бизнес-логикой.

Проект должен содержать:

* PostgreSQL как основную БД;
* существующий `postgres_driver.py` как инфраструктционный слой доступа к БД;
* `backend.py` как слой бизнес-логики;
* модели предметной области в `models/`;
* `app.py` как пользовательский интерфейс;
* автоматическое создание необходимых таблиц;
* полный CRUD для `User`, `Table`, `Booking`;
* проверку доступности столика;
* защиту от пересекающихся бронирований;
* валидацию бизнес-правил;
* тесты.

Не добавлять функциональность только ради увеличения объёма проекта.

Каждая дополнительная функция должна иметь понятное практическое обоснование.

---

## 5.2. Минимальная предметная модель

Основные сущности:

### User

Пользователь ресторана.

### Table

Столик ресторана.

Не использовать имя SQL-таблицы `table`, если это создаёт конфликт или неоднозначность с SQL-синтаксисом.

Допустимо использовать имя модели `Table`, а для PostgreSQL использовать понятное имя таблицы, например `restaurant_tables`.

### Booking

Бронирование столика пользователем на определённый интервал времени.

Связи:

```text
User 1 ─── N Booking N ─── 1 Table
```

Не создавать дополнительные сущности без необходимости.

---

## 5.3. Обязательные бизнес-правила бронирования

При создании или изменении бронирования необходимо проверять:

1. пользователь существует;
2. столик существует;
3. количество гостей больше нуля;
4. количество гостей не превышает вместимость столика;
5. время начала меньше времени окончания;
6. для одного столика не существует пересекающегося бронирования.

Проверка доступности должна учитывать именно временной интервал.

Для существующего бронирования при его изменении оно не должно конфликтовать само с собой.

---

## 5.4. Защита от пересекающихся бронирований

Недостаточно реализовать только последовательность:

```text
проверить доступность
        ↓
создать бронирование
```

если между этими операциями возможна конкуренция.

Операция создания бронирования должна быть атомарной.

При необходимости необходимо использовать существующий механизм транзакций `PostgresDriver.transaction()` и подходящий механизм блокировки PostgreSQL.

Нельзя создавать собственный connection pool или обходить `PostgresDriver`.

Цель:

```text
BEGIN
  ↓
проверка / блокировка
  ↓
создание бронирования
  ↓
COMMIT
```

При ошибке:

```text
ROLLBACK
```

Конкретный механизм блокировки должен быть выбран после анализа существующей архитектуры и возможностей PostgreSQL.

Не добавлять сложные механизмы конкурентности без необходимости.

---

## 5.5. Backend

`backend.py` является слоем бизнес-логики приложения.

В нём не должно быть кода Tkinter.

В `app.py` не должно быть SQL-запросов.

GUI вызывает backend, backend работает с PostgreSQL через `PostgresDriver`.

Основной поток:

```text
app.py
  ↓
backend.py
  ↓
PostgresDriver
  ↓
PostgreSQL
```

Backend отвечает за:

* валидацию входных данных;
* выполнение CRUD;
* проверку существования связанных сущностей;
* проверку вместимости;
* проверку временных интервалов;
* проверку доступности;
* предотвращение конфликтующих бронирований;
* обработку бизнес-ошибок.

---

## 5.6. Пользовательский интерфейс

Для frontend использовать Tkinter, если для выполнения требований проекта не требуется другой интерфейс.

GUI должен обращаться к backend и не содержать SQL или PostgreSQL-кода.

Минимальный интерфейс должен позволять:

* работать с пользователями;
* работать со столиками;
* создавать и просматривать бронирования;
* проверять доступность столика.

Команда или кнопка **«Проверить доступность»** обязательна.

Не создавать отдельный web-backend, REST API или frontend-фреймворк без явной необходимости.

---

## 5.7. SQL и целостность данных

Использовать только параметризованные SQL-запросы.

Не использовать:

* конкатенацию пользовательских данных в SQL;
* f-string для значений SQL;
* прямые подключения к PostgreSQL вне `PostgresDriver`.

Связи между сущностями должны обеспечиваться внешними ключами.

Для очевидных ограничений целостности использовать ограничения PostgreSQL, если это уменьшает вероятность некорректных данных.

Примеры:

* уникальный номер столика;
* вместимость столика больше нуля;
* количество гостей больше нуля;
* корректный временной интервал;
* корректные внешние ключи.

---

## 5.8. Автоматическое создание структуры БД

При запуске приложения необходимые таблицы должны создаваться автоматически, если они ещё отсутствуют.

Создание таблиц должно быть идемпотентным.

Повторный запуск приложения не должен приводить к ошибкам из-за уже существующих таблиц.

Не использовать ORM только ради автоматического создания таблиц.

---

## 5.9. Отсутствие демонстрационной реализации

Основная функциональность проекта не должна быть написана как demo/mock/prototype.

Не использовать:

* фиктивные данные вместо БД;
* заглушки вместо бизнес-логики;
* hardcoded bookings;
* fake availability;
* mock backend для основной работы приложения.

Если для выполнения задания необходимы тестовые записи пользователей, столиков и бронирований, они должны создаваться через реальную бизнес-логику приложения или отдельный контролируемый механизм инициализации данных.

Тестовые данные не должны быть частью основной логики приложения.

---

## 5.10. Необходимые тесты

Тесты должны проверять не только успешный сценарий.

Обязательно проверить:

* создание пользователя;
* создание столика;
* создание бронирования;
* получение бронирований;
* обновление и удаление сущностей;
* недопустимое количество гостей;
* превышение вместимости столика;
* некорректный временной интервал;
* конфликтующие бронирования;
* доступный временной интервал;
* изменение существующего бронирования без ложного конфликта;
* корректное поведение после ошибок транзакции.

Для критической логики доступности предпочтительнее проверять реальное поведение PostgreSQL, а не только имитировать БД.

---

## 5.11. Ограничение масштаба

Не добавлять без необходимости:

* FastAPI;
* Django;
* SQLAlchemy;
* Redis;
* Docker;
* Celery;
* микросервисы;
* JWT;
* систему ролей;
* платежи;
* email/SMS;
* внешние календарные сервисы;
* очереди сообщений;
* отдельную инфраструктуру деплоя.

Если новая технология действительно необходима, сначала объяснить пользователю причину и дождаться согласования.

Критерий качества проекта — не количество технологий, а корректность архитектуры и бизнес-логики.

---

## 6. Работа с SQL

Использовать параметризованные SQL-запросы.

Не подставлять пользовательские значения через конкатенацию строк или f-string.

Не изменять SQL-логику существующего драйвера.

---

## 7. Изменения файлов

Перед изменением существующего файла:

1. определить его назначение;
2. найти места его использования;
3. определить зависимости;
4. определить влияние изменения;
5. только после этого вносить минимальное изменение.

Не удалять и не переименовывать файлы без явного согласования с пользователем.

---

## 8. Тестирование

После каждого значимого изменения:

1. запустить соответствующие тесты;
2. проверить изменённый функционал;
3. убедиться, что существующая функциональность не сломана.

Перед завершением этапа выполнить доступные проверки проекта:

* pytest;
* mypy;
* flake8;
* py_compile.

Если тест падает, не скрывать проблему изменением теста.

Сначала определить причину ошибки.

---

## 9. Запрещено самостоятельно

Без явного указания пользователя агент не должен:

* менять `postgres_driver.py`;
* менять архитектуру проекта;
* удалять существующие тесты;
* ослаблять проверки;
* отключать линтеры;
* отключать type checking;
* менять конфигурацию PostgreSQL;
* менять `.env`;
* добавлять секреты в код;
* заменять рабочую реализацию на упрощённую;
* переписывать большие части проекта ради одной небольшой задачи.

---

## 10. Формат работы

Работать по принципу:

**изменили → проверили → зафиксировали → следующий шаг.**

Не выполнять несколько независимых крупных рефакторингов одновременно.

Перед крупным изменением сначала сообщить пользователю:

* что будет изменено;
* в каких файлах;
* зачем это необходимо;
* какие зависимости затрагиваются;
* каким тестом будет проверен результат.

---

## 11. При обнаружении проблемы в PostgresDriver

Если задача требует изменения `postgres_driver.py`, агент НЕ должен изменять файл самостоятельно.

Необходимо сообщить:

> Для реализации этой функции требуется изменение готового PostgreSQL-драйвера. Файл `postgres_driver.py` защищён правилами проекта и не должен изменяться без отдельного согласования.

После этого предложить вариант реализации на уровне приложения, если такой вариант возможен.

---

## 12. Приоритет правил

Приоритет:

1. безопасность;
2. сохранение существующей рабочей инфраструктуры;
3. корректность бизнес-логики;
4. тестируемость;
5. минимальность изменений;
6. читаемость и поддерживаемость;
7. косметические улучшения.

Не жертвовать рабочей функциональностью ради косметического рефакторинга.

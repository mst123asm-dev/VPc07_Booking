# Booking — Система бронирования столиков ресторана

Production-level приложение для управления бронированием столиков в ресторане.
PostgreSQL + Python backend + Tkinter GUI.

## Архитектура

```
app.py (Tkinter GUI)
  ↓
backend.py (BookingService — бизнес-логика)
  ↓
postgres_driver.py (PostgresDriver — инфраструктурный слой доступа к БД)
  ↓
PostgreSQL
```

| Компонент | Назначение |
|---|---|
| `app.py` | Tkinter GUI — управление клиентами, столиками и бронированиями, проверка доступности столика |
| `backend.py` | Слой бизнес-логики (`BookingService`) — валидация, CRUD, проверка доступности, защита от конфликтов |
| `postgres_driver.py` | Универсальный драйвер PostgreSQL на основе `psycopg2.pool.ThreadedConnectionPool` |
| `schema.py` | Идемпотентное создание SQL-схемы (`CREATE TABLE IF NOT EXISTS`) |
| `main.py` | Точка входа — загрузка `.env`, инициализация драйвера и схемы, запуск GUI |
| `models/` | Модели предметной области: `User`, `Table`, `Booking` |
| `tests/` | Интеграционные тесты с реальным PostgreSQL |
| `requirements.txt` | Зависимости Python-пакетов |
| `.env.example` | Шаблон переменных окружения (без секретов) |
| `.env` | Реальные переменные окружения (не публикуется) |

## Технологии

- Python 3.11+
- PostgreSQL
- `psycopg2-binary` — драйвер PostgreSQL
- `python-dotenv` — загрузка `.env`
- `tkinter` — десктопный GUI

## Возможности

### CRUD

- **User** — создание, чтение, обновление, удаление
- **Table** — создание, чтение, обновление, удаление
- **Booking** — создание, чтение, обновление, удаление

### Бизнес-правила

- Проверка существования клиента и столика
- Проверка вместимости столика (количество гостей ≤ capacity)
- Проверка корректности временного интервала (start < end)
- Предотвращение пересекающихся бронирований
- Разрешение соседних интервалов (полуоткрытые интервалы `[start_time, end_time)`)
- Проверка доступности столика через `check_table_availability()`

### Временные интервалы

Бронирования используют полуоткрытые интервалы `[start_time, end_time)`.

Примеры:

| Интервал 1 | Интервал 2 | Статус | Причина |
|---|---|---|---|
| 10:00–12:00 | 12:00–14:00 | ✅ Допустимо | Соседние, не пересекаются |
| 10:00–12:00 | 11:00–13:00 | ❌ Запрещено | Пересекаются |
| 10:00–12:00 | 13:00–15:00 | ✅ Допустимо | Не пересекаются |

### Операции в графическом интерфейсе

GUI (`app.py`) предоставляет управление клиентами, столиками и
бронированиями. Данные можно добавлять прямо в интерфейсе, а также
подготовить заранее (см. раздел «Первый запуск и наполнение базы»).

Доступные действия:

| Элемент интерфейса | Действие |
|---|---|
| Таблица «Клиенты» | Список клиентов (ID, имя, телефон) |
| Кнопка «Добавить» (Клиенты) | Создать клиента (имя, телефон) |
| Кнопка «Изменить» (Клиенты) | Изменить имя и телефон выбранного клиента |
| Кнопка «Удалить» (Клиенты) | Удалить выбранного клиента |
| Таблица «Столики» | Список столиков (ID, номер, вместимость, расположение) |
| Кнопка «Добавить» (Столики) | Создать столик (номер, вместимость, расположение) |
| Кнопка «Редактировать» (Столики) | Изменить номер, вместимость и расположение столика |
| Кнопка «Удалить» (Столики) | Удалить выбранный столик |
| Выпадающий список «Клиент» | Выбор клиента для бронирования |
| Кнопка «+ Новый клиент» | Быстро добавить клиента из формы бронирования |
| Выпадающий список «Столик» | Выбор существующего столика |
| Поле «Гостей» | Количество гостей (целое число > 0) |
| Поля «Начало»/«Окончание» | Интервал в формате `YYYY-MM-DD HH:MM` |
| Кнопка «Забронировать» | Создать бронирование |
| Кнопка «Проверить доступность» | Проверить доступность столика на интервал |
| Кнопка «Обновить список» | Перечитать бронирования из БД |
| Кнопка «Удалить выбранное» | Удалить выбранное бронирование |
| Таблица «Бронирования» | Список бронирований с ID, клиентом, столиком, гостями и интервалом |

Удалить клиента или столик, на которые ссылаются существующие
бронирования, нельзя: приложение покажет понятное сообщение, а запись
останется в базе.

### Защита от конкурентных бронирований

`create_booking()` и `update_booking()` выполняются в транзакции с использованием
`pg_advisory_xact_lock(table_id)` — блокировка берётся на столик, операции
сериализуются, и race condition исключается.

При обновлении бронирования (смена столика) блокировки на оба столика берутся
в детерминированном порядке (по возрастанию `table_id`), что исключает deadlock.

### Безопасность

- Все SQL-запросы параметризованы (`%s`-плейсхолдеры); конкатенация
  пользовательских данных в SQL не используется
- Учётные данные хранятся в `.env`, который исключён из репозитория через
  `.gitignore`
- `.env.example` содержит шаблон без реальных секретов
- В исходном коде приложения (`app.py`, `backend.py`, `main.py`, `schema.py`,
  `models/`, `postgres_driver.py`) нет захардкоженных паролей и строк подключения

## Конфигурация

Создайте файл `.env` на основе `.env.example`:

```env
DB_HOST=localhost
DB_PORT=5432

DB_USER=your_user
DB_PASSWORD=your_password
```

Укажите реальные учётные данные вашего PostgreSQL-сервера.
`.env` **не должен** попадать в репозиторий — он исключён через `.gitignore`.
`.env.example` можно использовать как шаблон.

### Подготовка схемы PostgreSQL

Приложение создаёт таблицы автоматически при запуске (`schema.init`):
`users`, `restaurant_tables`, `bookings`. Создание идемпотентно —
повторный запуск не вызывает ошибок.

От вас требуется только создать саму **базу данных** (пустую). Имя базы
указывается в `DB_NAME`. Пользователь `DB_USER` должен иметь права на
создание таблиц в этой базе.

## Первый запуск и наполнение базы

Штатный сценарий первого запуска выполняется полностью через GUI — отдельный
Python-скрипт или SQL-запросы **не требуются**.

1. Запустите приложение (см. «Запуск»): `python main.py`. При старте `main.py`
   вызывает `schema.init()`, который автоматически создаёт таблицы `users`,
   `restaurant_tables`, `bookings` (если их ещё нет). Создание идемпотентно.
2. Откройте раздел **«Клиенты»** и нажмите **«Добавить»** — создайте клиента,
   указав имя и телефон.
3. Откройте раздел **«Столики»** и нажмите **«Добавить»** — создайте столик,
   указав номер и вместимость (расположение необязательно).
4. В форме **«Бронирование»** выберите клиента и столик, укажите число гостей
   и интервал, нажмите **«Забронировать»**.

Для работы GUI нужны:

- минимум один **клиент** — поля `name` (имя) и `phone` (телефон);
- минимум один **столик** — поля `number` (номер) и `capacity` (вместимость
  больше нуля); `location` (расположение) необязательно.

Ограничения схемы: значения `users.phone` и `restaurant_tables.number` должны
быть **уникальными**, а `capacity` — больше нуля. При попытке добавить клиента
с уже занятым телефоном или столик с занятым номером приложение покажет
понятное сообщение.

Проверить, что записи добавлены, можно прямо в GUI: клиенты отображаются в
разделе «Клиенты», столики — в разделе «Столики».

### Альтернативы для предзаполнения (необязательно)

Если требуется заранее наполнить базу большим объёмом данных, это можно
сделать вне GUI. Такие способы **не нужны** для обычного первого запуска.

Через публичный слой бизнес-логики `BookingService` (`create_user()`,
`create_table()`):

```powershell
$script = @'
from dotenv import load_dotenv
load_dotenv()
import os
from postgres_driver import PostgresDriver
from backend import BookingService
from models.user import User
from models.table import Table

dsn = (
    f"host={os.environ['DB_HOST']} port={os.environ['DB_PORT']} "
    f"dbname={os.environ['DB_NAME']} user={os.environ['DB_USER']} "
    f"password={os.environ['DB_PASSWORD']}"
)
driver = PostgresDriver(dsn=dsn, min_conn=1, max_conn=3)
try:
    service = BookingService(driver)
    service.create_user(User(None, "Имя Гостя", "+7-000-000-00-01"))
    service.create_table(Table(None, "1", 2, "Зал"))
finally:
    driver.close()
'@
$script | python -
```

Или эквивалентными `INSERT`-запросами через `psql`:

```sql
INSERT INTO users (name, phone)
VALUES ('Имя Гостя', '+7-000-000-00-01');

INSERT INTO restaurant_tables (number, capacity, location)
VALUES ('1', 2, 'Зал');
```

`create_user()` и `create_table()` проходят штатную валидацию моделей и
возвращают объект с присвоенным из БД `id`. Повторное добавление того же
`phone` или `number` приведёт к ошибке уникальности — это ожидаемое поведение,
дубликаты не создаются.

## Запуск

```powershell
python main.py
```

При запуске `main.py` автоматически:
1. Загружает переменные окружения из `.env`
2. Создаёт подключение к PostgreSQL
3. Создаёт таблицы (`users`, `restaurant_tables`, `bookings`), если они ещё не существуют
4. Запускает Tkinter GUI

## Тесты

Тесты интеграционные и работают с реальным PostgreSQL. Они **не используют
mock** и подключаются к БД только через `PostgresDriver`.

### Безопасная тестовая база данных

`tests/test_config.py` содержит защиту от случайного запуска тестов против
рабочей базы. Тестовый драйвер подключается к базе `TEST_DB_NAME`, а не к
`DB_NAME`. Тесты разрешены только при одновременном выполнении условий:

```text
TEST_DB_NAME задана и не пуста
TEST_DB_NAME оканчивается на "_test"
TEST_DB_NAME отличается от имени рабочей БД (DB_NAME или POSTGRES_DB)
```

Имя рабочей БД определяется по текущей логике `DB_NAME or POSTGRES_DB`.
Тестовый DSN формируется с использованием `TEST_DB_NAME`.

При нарушении любого из условий `create_test_driver()` выбрасывает
`TestConfigError` до создания подключения. Это значит, что для запуска тестов
`.env` должен указывать на **выделенную тестовую базу**, например:

```env
DB_NAME=booking
TEST_DB_NAME=booking_test
```

Не запускайте тесты на базе с реальными рабочими данными. Тесты создают
собственные объекты и удаляют только их (`TestCleanupTracker`), но
безопаснее использовать отдельную БД.

### Запуск

Без установленного `pytest` каждый сценарий запускается как модуль:

```powershell
python -m tests.test_backend_integration
python -m tests.test_bookings
python -m tests.test_concurrency
python -m tests.test_transaction_recovery
```

Если `pytest` установлен:

```powershell
python -m pytest tests/
```

Все четыре сценария (включая `test_transaction_recovery`) используют реальный
PostgreSQL и не подменяют поведение драйвера. Тест `test_transaction_recovery`
дополнительно проверяет реальную ошибку PostgreSQL внутри `transaction()`
(`SELECT 1 / 0`) и восстановление соединения после неё.

## Защита секретов

- Никогда не коммитьте `.env` — он уже в `.gitignore`.
- Не добавляйте пароли, строки подключения и токены в исходный код,
  документацию и тесты.
- Для публикации используйте `.env.example` как шаблон без реальных значений.
- Перед первой фиксацией проверьте индекс Git на отсутствие `.env` и других
  секретов (см. раздел «Устранение типичных проблем»).
- `.gitignore` не перестаёт отслеживать файлы, уже добавленные в индекс,
  поэтому при необходимости файл нужно удалить из индекса отдельной командой
  (выполнять осознанно).

## Устранение типичных проблем

| Симптом | Вероятная причина | Что проверить |
|---|---|---|
| `Не заданы переменные окружения: ...` | В `.env` не заполнены обязательные переменные | Наличие `DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` |
| `Ошибка инициализации схемы` / не удаётся подключиться | PostgreSQL недоступен или неверные данные | Запущен ли сервер, верны ли хост/порт/логин/пароль |
| Пустые выпадающие списки в GUI | В БД нет клиентов/столиков | Добавить клиентов и столики в GUI |
| `TestConfigError: TEST_DB_NAME не задана` | Не настроена тестовая БД | Задать `TEST_DB_NAME` (не пустую, с суффиксом `_test`) |
| `TestConfigError: ... не оканчивается на '_test'` | Имя тестовой БД без суффикса `_test` | Указать в `TEST_DB_NAME` имя вида `booking_test` |
| `TestConfigError: ... совпадает с рабочей базой` | `TEST_DB_NAME` равно `DB_NAME` | Задать `TEST_DB_NAME`, отличную от рабочей БД |
| `Модуль tests... не найден` | Запуск не из корня проекта | Запускать команды из каталога проекта |
| `.env` уже попал в индекс Git | Файл был добавлен до настройки `.gitignore` | Удалить его из индекса отдельной командой, файл сохранится на диске |
